How does the standard ramp map brightness to characters?

The ramp is the ten characters .:-=+*#%@, ordered by ink. Each cell is one Rec. 709 luma value, and that value picks one of the ten: a dark cell is a space, a mid-tone lands on = or +, a highlight on % or @. All ten are 7-bit ASCII.

Start at 100–140 columns. Below that the ten steps still read, and the mid-tones hold if you raise contrast. The full comparison of all six charsets is on the home page.

[ tuning_and_compatibility ]

Where the standard ramp excels

$ 7-bit universal safety

Every glyph resides within classic US-ASCII (hex 0x20 to 0x7E). It renders without distortion across serial consoles, legacy VT100 terminals, commit messages, and plain-text emails.

$ optimal column widths

Use 100–140 columns for full-width desktop terminals. For mobile screens or GitHub README code blocks, keep the output within 60–72 columns to prevent horizontal scrolling.

$ contrast tuning

Because ten steps have wide tonal gaps, boosting contrast by +15 to +30 pushes indistinct midtones outward, yielding crisp edges and immediate visual readability.

[ faq ]

Standard ramp questions

Why use 10 characters instead of a 68-step detailed ramp?

The 10-step ramp prioritizes legibility and portability. At narrower widths (under 80 columns), subtle steps in a 68-character ramp blur together into visual noise. The standard ramp keeps each step visually distinct.

How does Semaphore calculate character luminance?

The engine samples canvas pixel data using standard Rec. 709 luma weights (Y = 0.2126*R + 0.7152*G + 0.0722*B), matching human perception of green, red, and blue brightness.

How to paste standard ASCII art into GitHub README without breaking?

Always place the copied text inside a fenced code block opened with ```text. Standard Markdown collapses multiple consecutive spaces outside code blocks, which would destroy the spacing that forms the picture.
